{BRAND_NAME} seals every device credential to the zone that will use it and stores only the ciphertext. Brokkr (the hub) cannot open its own secret store, so a stolen hub database yields no BMC passwords. The tokens servers use to phone home are hashed with a server-side pepper that is never stored in the database. Neither table is worth exfiltrating on its own.

## Sealed to the custody zone

A **device secret** stores one out-of-band credential per device and purpose. The purpose is `BMC` (IPMI/Redfish) or `CONSOLE` (serial-over-LAN). The credential itself can be a user/password pair, a key, a token, or a certificate.

When an operator writes a secret, Brokkr seals the plaintext to the custody zone's enrolled X25519 public key. The seal is an authenticated Diffie-Hellman envelope with AES-256-GCM, and Brokkr persists only the envelope (`ephPub`, `ciphertext`, `tag`). The custody zone's Bridge (the spoke) holds the matching private key and is the only component that can open the envelope.

The envelope's authenticated data is derived from the row itself: the zone, the sealing enrollment's ID, the device, the purpose, the kind, and the key generation. It is never stored. A ciphertext therefore cannot be replayed against a different device, zone, or enrollment, even an enrollment with a matching generation.

Two properties follow:

- **Versions are append-only.** Each write appends a new version per (device, purpose). The current secret is the highest version not marked invalidated. Invalidation marks rows in place. Secret rows are removed only by the schema-level cascade when their device is deleted.
- **Sealing requires the hub key.** If `BROKKR_HUB_PRIVATE_KEY` is unset, hub crypto is dormant. Writes and reveals are refused up front instead of failing later.

Zone keys are established during Bridge enrollment. See [Create and enroll a zone](/zones/create-and-enroll). The registration token itself is one-time and stored only as a SHA-256 hash.

## Re-enrollment invalidates old seals

Every seal records the zone's enrollment `generation` as `keyGen`. Re-enrolling a zone replaces its key pair and increments the generation. Every envelope sealed to the old generation becomes permanently unopenable, because the new key cannot decrypt it. This is intentional.

Re-enrollment invalidates every live older-generation secret in the same transaction that consumes the registration token, and records an `INVALIDATED` audit event with cause `ZONE_REENROLLED` for each. As a backstop, any row that escapes that sweep is caught on the next read or version listing. Brokkr marks the row invalidated and records an audit event with cause `STALE_ZONE_KEY`. In both cases the operator must re-enter the credential. There is no silent fallback to a stale seal.

## The audited reveal flow

Reading a stored credential back in plaintext takes a full round-trip to the custody zone, and every step is recorded in the audit trail. A reveal requires an interactive instance-operator session (API keys are rejected), the `device-secret:access` permission, and active hub crypto.

1. **Request.** The operator requests a reveal of a specific version. Brokkr records `REVEAL_REQUESTED` and enqueues a `secret_reveal` job carrying the sealed envelope to the custody zone's Bridge. The call returns a request ID.
2. **Open.** The Bridge opens the envelope with its zone private key and returns the plaintext on the results queue.
3. **Stash.** Brokkr encrypts the plaintext into a short-lived Redis stash with a 30-second TTL. The stash uses AES-256-GCM under a key derived from the hub private key and is bound to the device and request ID.
4. **Deliver.** The operator polls the reveal status. The first successful poll consumes the stash atomically with `GETDEL` and records `REVEAL_DELIVERED`. The response returns the secret with `no-store` cache headers.

Routine provisioning never reveals anything. Brokkr reads the current sealed envelope and forwards it to the custody zone, where the Bridge opens it locally. Brokkr records a `DISPATCH` audit event for each dispatch. On this path the audit write is best-effort. A failed audit insert is logged and the envelope is still dispatched. When Brokkr seals a credential on the fly for dispatch, a failed audit insert aborts the seal, so an ephemeral seal is never handed out without a durable record.

Audit rows are append-only and never contain secret material. They are keyed to the device ID without a foreign key, so deleting a device cannot erase its disclosure history. See [Audit and event log](/security/audit-and-event-log).

## Per-device phone-home tokens

Every server authenticates its phone-home callbacks with an opaque bearer token minted per device. A token is 32 random bytes, stored only as an HMAC-SHA256 hash keyed by the `DEVICE_TOKEN_PEPPER` secret. The pepper lives in the hub's environment and never in the database. Brokkr fails closed at startup if the pepper is unset or blank. A database dump yields hashes that cannot be matched without the pepper. The plaintext is returned only to the device itself when the token is minted or rotated. Everywhere else the token appears only as a `dtok_`-prefixed display ID. This includes database rows and server logs.

<Warning>Rotating the pepper invalidates every issued token at once. Devices must re-provision.</Warning>

Each token carries a context that tells Brokkr which OS is calling:

| Context         | Runs as                  | Expiry                                                               | Lifecycle meaning                                                                               |
| --------------- | ------------------------ | -------------------------------------------------------------------- | ----------------------------------------------------------------------------------------------- |
| `BROKKR_LIVE`   | the discovery OS         | 24 hours by default (`DEVICE_TOKEN_BROKKR_LIVE_TTL_SECONDS`)         | During provisioning, keeps the device `provisioning` because the ordered OS has not booted yet. |
| `DEPLOYMENT_OS` | the deployed customer OS | none; tied to the deployment and revoked when the deployment changes | During provisioning, proves the ordered OS booted and sets the device to `provisioned`.         |

The same distinction guards teardown. A `DEPLOYMENT_OS` phone-home while a device is deprovisioning means the wipe failed and the customer OS booted again, so Brokkr marks the device `failed` instead of releasing it. See [Deployment lifecycle](/deployments/lifecycle).

Only one token per device and context is active at a time. Issuing a replacement revokes its predecessor in the same transaction. Revoking a `BROKKR_LIVE` token also deletes the published token material from the zone.

## Typed revocations and misuse detection

Every revocation records a reason:

| Reason             | Meaning                                     |
| ------------------ | ------------------------------------------- |
| `DEPLOYMENT_ENDED` | The deployment the token belonged to ended. |
| `REPROVISION`      | The device was reprovisioned with a new OS. |
| `ROTATION`         | Routine replacement by a newer token.       |

Presenting a revoked token records a `USED_AFTER_REVOKE` audit event with the caller's IP and user agent before the request is rejected. Presenting an expired token records `USED_AFTER_EXPIRY`. Together with the `ISSUED`, `ROTATED`, and `REVOKED` events, the token audit trail shows who holds a credential and who tried to use one after revocation or expiry. For the wider security model, see [Security](/brokkr-security).
